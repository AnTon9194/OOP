# Звіт. Самостійна робота №13


## 1. Опис реалізації

Клас `Cache<TKey, TValue>` (обмеження `where TKey : notnull`) має три приватні поля:

- `_capacity` — максимальна кількість елементів;
- `_cache` (`Dictionary<TKey, TValue>`) — зберігання пар ключ-значення, доступ за O(1);
- `_keysOrder` (`Queue<TKey>`) — порядок додавання ключів.

Публічний інтерфейс: конструктор `Cache(int capacity)`, `Add`, `Get`, `ContainsKey` і властивість `Count`.

**Ключові рішення:**

- Конструктор кидає `ArgumentOutOfRangeException`, якщо ємність ≤ 0.
- `Add`: якщо кеш повний, `Dequeue()` дає найстаріший ключ, який видаляється зі словника. Потім додається новий елемент.
- Повторне `Add` з існуючим ключем лише оновлює значення і не змінює позицію в черзі. Інакше в черзі з'явилися б дублікати ключів, і видалення працювало б хибно.
- `Get` використовує `TryGetValue`, тож виняток `KeyNotFoundException` формується з зрозумілим повідомленням.

## 2. Юніт-тести

Усього 13 тестів, що покривають кожен публічний член:

| Група | Що перевіряється |
|---|---|
| Конструктор | ємність 0 та від'ємна кидають `ArgumentOutOfRangeException` |
| `Add` | новий елемент зберігається; існуючий ключ оновлює значення без зміни `Count` |
| `Get` | повертає значення; для відсутнього ключа кидає `KeyNotFoundException` |
| Переповнення (FIFO) | видаляється найстаріший; порядок видалення відповідає порядку додавання; `Get` не впливає на порядок; оновлення ключа в повному кеші нічого не витісняє; ємність 1 |
| `ContainsKey` | `true` для наявного, `false` для відсутнього ключа |
| `Count` | 0 для нового кешу; ніколи не перевищує ємність |

## 3. Демонстрація в `Main`

Створюється `Cache<string, string>` ємністю 3. Додаються 3 елементи, виконується `Get`, потім додається 4-й, що витісняє `"UA"`. Спроба отримати `"UA"` кидає виняток.

Очікуваний вивід:

```

=== Додаємо 4-й елемент: кеш переповнюється ===
ContainsKey("UA") = False
ContainsKey("PL") = True
ContainsKey("DE") = True
ContainsKey("FR") = True
Count = 3

=== Звернення до видаленого ключа ===
Виняток: Ключ 'UA' не знайдено в кеші.
```

## 4. Додатково: розширення до LRU

Щоб перетворити FIFO на LRU, замінюємо `Queue<TKey>` на `LinkedList<TKey>`. При кожному `Get` та `Add` існуючого ключа переносимо його в кінець списку, а видаляємо перший елемент. Тест `Get_DoesNotAffectEvictionOrder_InFifo` у такому разі треба інвертувати.

## 5. Висновки

Реалізовано узагальнений FIFO-кеш на базі `Dictionary` та `Queue`. Поєднання двох структур дало швидкий доступ за ключем і швидке витіснення. Тести покривають усі публічні методи та крайні випадки, зокрема ємність 1 і оновлення існуючого ключа.

## 6. Відповіді на контрольні запитання

**1. Які переваги надає `Cache<TKey, TValue>` порівняно з окремими неузагальненими реалізаціями?**
Один клас замість окремих `StringCache`, `IntCache` тощо, тож немає дублювання коду. Типобезпека перевіряється на етапі компіляції, без приведення типів. Для типів-значень немає boxing/unboxing, а отже менше навантаження на GC. Код легше тестувати й підтримувати: виправлення помилки в одному місці діє для всіх типів.

**2. Чому для FIFO зручно поєднувати `Dictionary` з `Queue` або `LinkedList`?**
Кожна структура відповідає за своє. `Dictionary` дає пошук за ключем за O(1), але не гарантує порядку. `Queue` зберігає порядок додавання, а `Dequeue()` за O(1) видає найстаріший ключ. Разом вони забезпечують швидкий доступ і швидке витіснення. `LinkedList` потрібен для LRU: він дозволяє перемістити ключ у кінець списку й вилучити будь-який вузол, чого `Queue` не вміє.

**3. Коли `Get` має кидати `KeyNotFoundException`, а коли краще підхід `TryGetValue`?**
Виняток доречний, коли відсутність ключа означає помилку в логіці й викликач очікує, що ключ є. Підхід `TryGetValue` (повертає `bool` + `out`) кращий, коли відсутність є звичайною ситуацією, наприклад при кешуванні: промах кешу очікуваний, а після нього дані завантажують з джерела. Виняток тут був би повільним і зайвим. Практично обидва підходи часто надають разом: `Get` і `TryGet`.

**4. Які тести критично важливі для перевірки політики витіснення?**
- При переповненні видаляється саме найстаріший елемент, а новіші залишаються.
- Порядок видалення відповідає порядку додавання (кілька витіснень поспіль).
- `Count` ніколи не перевищує ємність.
- Оновлення існуючого ключа не витісняє нічого й не змінює порядок.
- `Get` не впливає на порядок витіснення (у FIFO).
- Ємність 1 як крайній випадок.
- Звернення до витісненого ключа кидає `KeyNotFoundException`.
