# Самостійна робота №15 — Делегати й лямбда-вирази: власні утиліти для колекцій

## Що реалізовано
Статичний клас `CollectionUtils` з чотирма узагальненими методами:

| Метод | Делегат | Аналог LINQ |
|---|---|---|
| `Map<TSource,TResult>` | `Func<TSource,TResult>` | `Select` |
| `MaxBy<T,TKey>` (`where TKey : IComparable<TKey>`) | `Func<T,TKey>` | `MaxBy` |
| `Filter<T>` | `Predicate<T>` | `Where` |
| `ForEach<T>` | `Action<T>` | `List<T>.ForEach` |

Додатково: перевірка аргументів на `null`; `MaxBy` на порожній колекції кидає `InvalidOperationException` (замість мовчазного повернення `default`).

Демонстрація виконана на трьох колекціях: `List<int>`, `List<string>`, `List<Product>` з різними лямбдами.

## Звіт

### Чому делегати корисні для таких утиліт?
Делегат дозволяє **передати поведінку як параметр**. Метод `Filter` знає лише *як* обійти колекцію, а *що* вважати відповідним — визначає викликач. Тому один метод замінює десятки специфічних («відфільтрувати дорогі», «відфільтрувати парні» тощо), а алгоритм обходу не дублюється.

### Як лямбда-вирази спрощують виклик?
Без лямбд довелося б писати окремий іменований метод для кожної умови. Лямбда — це вбудований анонімний метод прямо в місці виклику: `p => p.Price > 1000`. Вона може «захоплювати» локальні змінні, а компілятор сам виводить типи параметрів (`TSource`, `TResult`, `TKey`), тому явно вказувати узагальнені аргументи не треба.

### Порівняння з LINQ
| | Власні методи | LINQ |
|---|---|---|
| Виконання | **Жадібне** (`List`, результат готовий одразу) | **Відкладене** (`yield`, обчислюється при переборі) |
| Великі/нескінченні послідовності | Усе накопичується в пам'яті | Обробка потоково |
| Ланцюжки | Вкладені виклики | Fluent-синтаксис `.Where().Select()` |
| Перевірка аргументів, оптимізації (`Count`, `ElementAt`) | Базова | Розширена |
| Навчальна цінність | Видно, що відбувається «під капотом» | Готовий і протестований інструмент |

### Висновки
Власні `Map`/`Filter`/`MaxBy`/`ForEach` — це по суті спрощені `Select`/`Where`/`MaxBy`. Вони допомагають зрозуміти делегати й generic-методи, але в продакшн-коді краще користуватися LINQ. Різниця в семантиці (жадібне vs відкладене виконання) — найважливіший практичний висновок.

## Відповіді на контрольні запитання
1. **Чому делегати зручні для передавання поведінки.** Вони типізовані, дозволяють параметризувати алгоритм логікою викликача, не створюючи класів/інтерфейсів для кожного випадку.
2. **`Func` / `Action` / `Predicate`.** `Func<T,TResult>` — приймає параметри й **повертає** значення (останній параметр типу — результат). `Action<T>` — приймає параметри, **нічого не повертає** (`void`). `Predicate<T>` — приймає `T` і повертає `bool` (еквівалент `Func<T,bool>`).
3. **Переваги generic + лямбда.** Один код працює з будь-яким типом із повною типобезпекою; менше шаблонного коду; логіка читається в місці виклику; компілятор виводить типи.
4. **Коли писати власні утиліти.** Для навчання; коли LINQ недоступний (старі платформи, обмежений runtime); коли потрібна специфічна семантика (інша обробка порожньої колекції, логування, жадібне виконання); коли потрібна доменна утиліта, якої немає в LINQ.
