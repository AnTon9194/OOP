# Звіт. Самостійна робота №19

## 1. Власний тип винятку

Предметна область: банківські операції. Клас `InsufficientFundsException : Exception` має властивості `RequestedAmount` і `CurrentBalance`, три стандартні конструктори (без параметрів, з `message`, з `message` та `innerException`) і додатковий конструктор з контекстом помилки.

У `Main` виняток демонструється блоком `try-catch-finally`: при спробі зняти 250 грн з рахунку на 100 грн перехоплюється `InsufficientFundsException`, виводиться повідомлення й розмір нестачі, а `finally` повідомляє про завершення операції.

## 2. Сценарії Polly

### Сценарій 1. Зовнішнє API погоди: Retry

**Проблема.** Зовнішнє API іноді повертає `503` через короткочасне перевантаження. Збій тимчасовий, і повторний запит через мить, найімовірніше, спрацює.

**Стратегія та обґрунтування.** Retry з експоненційною затримкою (0.5с → 1с → 2с) та jitter. Експоненційна затримка дає сервісу час відновитися, а jitter не дозволяє багатьом клієнтам повторювати запити одночасно. Повторюємо лише `HttpRequestException`, а не всі винятки: помилки програмування повторювати безглуздо. Операція (читання погоди) ідемпотентна, тому повтор безпечний.

**Фрагмент коду:**

```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(500),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        OnRetry = args => { /* логування спроби */ return default; }
    })
    .Build();
```

**Опис виводу** (затримки приблизні через jitter):

```
=== Сценарій 1: Retry (зовнішнє API) ===
  Виклик API, спроба 1...
  Retry #1 через 0.4с: 503 Service Unavailable
  Виклик API, спроба 2...
  Retry #2 через 0.6с: 503 Service Unavailable
  Виклик API, спроба 3...
  Успіх: +18°C, хмарно

```

Перші дві спроби невдалі, і кожна логується в `OnRetry`. Третя успішна, тож користувач отримує результат і не бачить збоїв.

### Сценарій 2. База даних: Circuit Breaker

**Проблема.** БД недоступна надовго (перезапуск, падіння вузла). Якщо кожен запит повторювати, застосунок витрачатиме потоки й час на безнадійні виклики та ще й заважатиме БД відновитися.

**Стратегія та обґрунтування.** Circuit Breaker, оскільки тривалий потік збоїв означає, що простий Retry шкодить. Вимикач має три стани. У *Closed* запити проходять, збої рахуються. Після досягнення порога (≥3 запити, ≥50% збоїв) він переходить в *Open* і відхиляє запити миттєво через `BrokenCircuitException`. Через 2с він стає *Half-Open* і пропускає пробний запит. Якщо той успішний, вимикач повертається в *Closed*.

**Фрагмент коду:**

```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<InvalidOperationException>(),
        FailureRatio = 0.5,
        MinimumThroughput = 3,
        SamplingDuration = TimeSpan.FromSeconds(10),
        BreakDuration = TimeSpan.FromSeconds(2),
        OnOpened = args => { /* логування */ return default; },
        OnHalfOpened = _ => { /* логування */ return default; },
        OnClosed = _ => { /* логування */ return default; }
    })
    .Build();
```

**Опис виводу** (скорочено):

```
=== Сценарій 2: Circuit Breaker (база даних) ===
  Запит #1 до БД...
  Запит #1 невдалий: Не вдалося підключитися до БД
  Запит #2 до БД...
  Запит #2 невдалий: Не вдалося підключитися до БД
  Запит #3 до БД...
  >>> Вимикач РОЗІМКНЕНО на 2с
  Запит #3 невдалий: Не вдалося підключитися до БД
  Запит #4 відхилено миттєво (коло розімкнене)
  Запит #5 відхилено миттєво (коло розімкнене)
  Запит #6 відхилено миттєво (коло розімкнене)
  ...чекаємо 2.5с, БД відновлюється...
  >>> Вимикач НАПІВРОЗІМКНЕНО (пробний запит)
  Запит #7 до БД...
  Запит #7 успішний
  >>> Вимикач ЗАМКНЕНО (сервіс відновився)
  Запит #8 до БД...
  Запит #8 успішний

```

Після трьох збоїв запити #4–#6 до БД не доходять, а відхиляються миттєво. Це і є захист ресурсів. Після паузи пробний запит #7 проходить, і система повертається до норми.

### Сценарій 3. Сервіс курсів валют: Timeout + Fallback

**Проблема.** Сервіс не падає, а просто відповідає повільно. Без обмеження часу користувач чекає невизначено довго.

**Стратегія та обґрунтування.** Timeout (1с) обмежує очікування. Fallback замість помилки віддає останній кешований курс. Retry тут не потрібен: повторення до повільного сервісу лише збільшить затримку. Для курсу валют трохи застаріле значення краще за відсутність відповіді.

**Фрагмент коду:**

```csharp
var pipeline = new ResiliencePipelineBuilder<string>()
    .AddFallback(new FallbackStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>().Handle<TimeoutRejectedException>(),
        FallbackAction = _ => Outcome.FromResultAsValueTask("41.50 (кешоване значення)")
    })
    .AddTimeout(TimeSpan.FromSeconds(1))
    .Build();
```

Порядок стратегій важливий: першою додається зовнішня (Fallback), далі внутрішня (Timeout). Timeout кидає `TimeoutRejectedException`, а Fallback її перехоплює.

**Опис виводу:**

```
=== Сценарій 3: Timeout + Fallback (курс валют) ===
  Запит курсу USD/UAH (сервіс відповідає 3с)...
  Fallback: використовуємо кешований курс
  Курс: 41.50 (кешоване значення)

[user@archlinux IndependentWork19]$ 

```

Через 1с `CancellationToken` скасовує очікування, Timeout кидає `TimeoutRejectedException`, а Fallback підставляє кешоване значення. Користувач отримує відповідь за ~1с замість 3с.

## 3. Винятки чи `Result<T>`

Виняток слід кидати в справді виняткових ситуаціях, коли метод не може виконати свій контракт: розірване з'єднання з БД, файл не знайдено, пошкоджений формат даних, брак коштів на рахунку, коли це порушує бізнес-інваріант. Виняток важко проігнорувати, він несе стек викликів, але розкрутка стека повільна, а порожній `catch` може «проковтнути» помилку.

`Result<T>` (або `bool`, `null`, `TryXxx`) доречний для очікуваних неуспіхів, які трапляються регулярно й є частиною нормального потоку: валідація введення користувача, пошук елемента, якого може не бути, промах кешу. Тут помилка є частиною сигнатури методу, це швидше, а код читається явніше. Мінус у тому, що результат можна випадково не перевірити. Правило: якщо виклик закономірно може «не спрацювати», повертайте Result, а якщо ситуація аварійна, кидайте виняток.

## 4. Загальні висновки щодо Polly

**Переваги:**

- Декларативний опис політик замість ручних циклів `try/catch` і `Thread.Sleep`.
- Готові стратегії (Retry, Circuit Breaker, Timeout, Fallback, Rate Limiter, Hedging), які легко комбінувати в одному пайплайні.
- Вбудована підтримка backoff і jitter, телеметрія та колбеки для логування.
- Прозора інтеграція з `HttpClient` і DI (`Microsoft.Extensions.Resilience`).

**Обмеження:**

- Polly не лікує постійні збої: вона лише маскує тимчасові.
- Неправильні налаштування шкодять: надто агресивний Retry створює «шторм» запитів, а надто короткий Timeout дає хибні відмови.
- Retry небезпечний для неідемпотентних операцій (платіж може списатися двічі).
- Порядок стратегій у пайплайні впливає на поведінку, і це легко переплутати.
- Додає складність і потребує тестування політик та моніторингу.

## 5. Відповіді на контрольні запитання

**1. Різниця між «кидати виняток» і «повертати Result».**
Виняток сигналізує про виняткову ситуацію, що порушує контракт методу, наприклад `File.ReadAllText` для неіснуючого файлу кидає `FileNotFoundException`. `Result` описує очікуваний неуспіх у сигнатурі, наприклад `int.TryParse("abc", out _)` повертає `false`, а валідація форми повертає `Result` зі списком помилок. Виняток повільніший, але його складно ігнорувати. Result швидший і явніший, але його можна не перевірити.

**2. Три стандартні конструктори власного винятку.**
Без параметрів: `MyException()`. З повідомленням: `MyException(string message)`. З повідомленням і внутрішнім винятком: `MyException(string message, Exception innerException)`. Останній дозволяє зберегти початкову причину помилки при обгортанні.

**3. Circuit Breaker і Retry.**
Retry повторює невдалу операцію в надії, що збій тимчасовий. Circuit Breaker після серії збоїв перестає викликати сервіс узагалі й відхиляє запити миттєво, даючи йому час відновитися. Retry доцільний при коротких, випадкових збоях (мережеві глітчі, 503). Circuit Breaker потрібен, коли збій тривалий і повтори лише навантажують проблемний сервіс та витрачають ресурси клієнта. Часто їх поєднують: Retry всередині, Circuit Breaker зовні.

**4. Bulkhead.**
Bulkhead ізолює ресурси (потоки, з'єднання, кількість одночасних викликів) між різними операціями. Він вирішує проблему каскадних відмов: повільний або несправний сервіс не може «з'їсти» всі ресурси застосунку. Наприклад, ліміт у 10 одночасних запитів до зовнішнього API гарантує, що решта застосунку продовжить працювати.

**5. Чому важливий Jitter.**
Без jitter усі клієнти, що отримали збій одночасно, повторюють запит в однакові моменти (1с, 2с, 4с...). Це створює синхронні піки навантаження («thundering herd»), які можуть знову «покласти» сервіс, що відновлюється. Випадкова складова розсіює повтори в часі й вирівнює навантаження.

**6. Ризики Retry для неідемпотентної операції.**
Якщо операція виконалась, але відповідь загубилась (таймаут, обрив з'єднання), повтор виконає її вдруге: подвійне списання коштів, дубльоване замовлення, повторне надсилання листа. Для таких операцій потрібні ключі ідемпотентності (idempotency key), перевірка стану перед повтором, або не застосовувати Retry взагалі.
