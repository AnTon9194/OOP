# Самостійна робота №20 — Реалізація exponential backoff


## Реалізація
`RetryPolicy` з полями `_maxRetries`, `_initialDelay`, `_jitterFactor` та методом
`T Execute<T>(Func<T> operation, Func<Exception, bool>? shouldRetry = null)`.

Формула затримки (за завданням):
```
delay = initialDelay * 2^retryAttempt * (1 + random.NextDouble() * jitterFactor * 2 - jitterFactor)
```
Множник jitter лежить у діапазоні `[1 − jitterFactor; 1 + jitterFactor]`, тобто при `0.2` це ±20%.

Логіка:
1. `maxRetries` — кількість **повторних** спроб, тож усього спроб `maxRetries + 1`.
2. При винятку: якщо спроби вичерпано **або** `shouldRetry` повернув `false` — виняток передається далі через `throw;` (зберігається оригінальний стек).
3. Інакше обчислюється затримка, логується, і виконується `Thread.Sleep`.
4. Кожна спроба, затримка й причина невдачі логуються через `Console.WriteLine`.
5. Параметри конструктора валідуються.

## Демонстрація (`Main`)
Параметри: `maxRetries = 4`, `initialDelay = 200 мс`, `jitterFactor = 0.2`.

| Сценарій | Що показує |
|---|---|
| 1 | операція падає двічі, на 3-й спробі успішна → `Execute` повертає результат |

| 3 | `shouldRetry` відхиляє `ArgumentException` → виняток одразу, без повторів |

## Висновок: межі застосування Retry з exponential backoff
Патерн підходить для **тимчасових, самовідновлюваних збоїв** (мережеві помилки, 503, тайм-аути, блокування БД), коли повторна спроба має шанс на успіх. Він **не підходить**, якщо:
- помилка постійна й не зникне (некоректні дані, 400/404, помилка автентифікації) — повтор лише марнує ресурси; для цього й потрібен `shouldRetry`;
- операція **неідемпотентна** (списання коштів, створення замовлення): повтор може виконати дію двічі;
- збій тривалий — краще Circuit Breaker, щоб не навантажувати «впалий» сервіс;
- потрібна низька затримка відповіді: сумарний час очікування зростає експоненційно (200+400+800+1600 мс ≈ 3 с);
- повторюється синхронний виклик у потоці UI/запиту — `Thread.Sleep` блокує потік (для продакшну — `async`-варіант з `Task.Delay`).
Завжди обмежуйте кількість спроб і максимальну затримку, а jitter не дає багатьом клієнтам повторювати запити одночасно.

## Відповіді на контрольні запитання
1. **Чому експоненційна затримка ефективніша за фіксовану.** Перші повтори швидкі (якщо збій дуже короткий), а подальші дають сервісу дедалі більше часу на відновлення й зменшують навантаження на нього; фіксована затримка або надто повільна для коротких збоїв, або надто агресивна для довгих.
2. **Jitter.** Випадкова складова розсинхронізує клієнтів: замість того щоб усі повторювали запит в один момент (1 с, 2 с, 4 с…) і знову перевантажували сервіс, повтори розподіляються в часі.
3. **Роль `shouldRetry`.** Дозволяє відрізнити тимчасові помилки (повторити) від постійних (не повторювати, одразу кинути виняток), не змінюючи код політики.
4. **Коли повтор небезпечний.** Для неідемпотентних операцій; при помилках валідації/автентифікації/авторизації; коли відповідь могла загубитись, а дія вже виконалась; коли сервіс явно перевантажений і повтори погіршать ситуацію.
