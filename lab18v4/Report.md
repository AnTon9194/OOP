## 2. Відповіді на контрольні запитання

### 1. Які типи винятків найчастіше виникають при роботі з файлами та мережею?

**Файли та потоки (простір імен `System.IO`):**
- `FileNotFoundException` — файл не знайдено;
- `DirectoryNotFoundException` — не знайдено директорію;
- `IOException` — загальна помилка вводу/виводу (файл зайнятий іншим процесом, диск заповнений, обрив читання);
- `UnauthorizedAccessException` — немає прав доступу;
- `PathTooLongException`, `EndOfStreamException`.

**Мережа:**
- `HttpRequestException` — помилка HTTP-запиту (немає з'єднання, помилка DNS, неуспішний статус-код у `EnsureSuccessStatusCode`);
- `SocketException` — помилка на рівні сокетів (відмова у з'єднанні, розрив);
- `TaskCanceledException` / `TimeoutException` — вичерпано час очікування;
- `WebException` — у застарілих API (`WebClient`, `HttpWebRequest`).

Порядок `catch` має йти від конкретніших винятків до загальніших: `FileNotFoundException` перед `IOException`, а той перед `Exception`.

### 2. Поясніть принцип роботи патерну Retry. Коли його доцільно використовувати?

Патерн Retry (повторна спроба) полягає в тому, що операцію, яка завершилась помилкою, виконують повторно, припускаючи, що причина тимчасова. Після невдачі перевіряють, чи помилка підлягає повтору і чи не вичерпано ліміт спроб. Якщо так, чекають (зазвичай з наростаючою паузою) і повторюють. Якщо ні, виняток передають далі.

**Доцільно використовувати** для *тимчасових (transient)* збоїв:
- короткочасна втрата мережі, таймаут, перевантаження сервера (HTTP 503, 429);
- блокування файлу іншим процесом;
- тимчасова недоступність БД або мікросервісу.

**Недоцільно** для постійних помилок (неправильний пароль, 404 для неіснуючого ресурсу, помилки валідації, пошкоджений файл) та для неідемпотентних операцій без додаткового захисту, наприклад повторного списання коштів. Кількість спроб потрібно обмежувати, інакше система може зависнути або перевантажити сервіс, що й так відмовляє.

### 3. Як реалізувати експоненційну затримку між повторними спробами?

Час очікування збільшується вдвічі після кожної невдачі:

```
delay = initialDelay * 2^attempt
```

Для `initialDelay = 200 мс` послідовність така: 200, 400, 800, 1600 мс. У коді:

```csharp
TimeSpan delay = TimeSpan.FromTicks(initialDelay.Ticks * (1L << attempt));
Thread.Sleep(delay);   // в асинхронному коді — await Task.Delay(delay)
```


### 4. Для чого потрібен делегат shouldRetry у допоміжному класі RetryHelper?

`shouldRetry` (`Func<Exception, bool>`) дозволяє викликаючому коду самому вирішувати, **для яких винятків** варто повторювати спробу. `RetryHelper` залишається універсальним і не знає про конкретні типи помилок, а політика задається ззовні.

Це потрібно, бо:
- тимчасові помилки (`HttpRequestException`, `FileNotFoundException` у нашому сценарії) мають сенс повторювати;
- постійні помилки (`IOException` через пошкоджений файл, `ArgumentException`) повторювати безглуздо: це лише марнує час і ресурси;
- політику можна робити гнучкою, наприклад повторювати лише при HTTP 5xx, але не при 4xx.

Якщо `shouldRetry` не передано (`null`), повторюються спроби для будь-якого винятку.

## 3. Висновки

У роботі опрацьовано обробку файлових і мережевих винятків за допомогою `try-catch-finally` та реалізовано узагальнений клас `RetryHelper` з експоненційною затримкою, логуванням і вибірковою політикою повторів через `shouldRetry`. Патерн Retry підвищує відмовостійкість застосунку при тимчасових збоях, але його слід застосовувати лише до помилок, що можуть зникнути самі, і з обмеженою кількістю спроб.
