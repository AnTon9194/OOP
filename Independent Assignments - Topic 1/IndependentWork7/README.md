# Самостійна робота №7 з ООП

## Звіт з виконання завдання

### Сценарій 1: Система сповіщень

#### Обраний підхід: Інтерфейс `INotifier`

#### Обґрунтування вибору:
У цьому сценарії використано **інтерфейс**, оскільки:
1. **Відсутність спільного стану та реалізації:** Канали сповіщень (Email, SMS, Push) суттєво відрізняються за технічною реалізацією. У них немає спільного коду чи полів (наприклад, Email працює з SMTP, SMS з GSM-шлюзом, Push з токенами пристроїв).
2. **Підтримка множинної поведінки:** Клас, що є сповіщувачем, у реальному проєкті може виконувати й інші ролі (наприклад, бути логером `ILogger` або підписником подій `IEventListener`). Використання інтерфейсів дає змогу реалізувати кілька контрактів одночасно, уникаючи обмеження одиночного успадкування.
3. **Слабке зв'язування (Decoupling):** Інтерфейс визначає лише контракт `Send(string message)`. Клієнтський код залежить від абстракції, що відповідає принципу інверсії залежностей (DIP із SOLID) та спрощує модульне тестування (mocking).

#### Чому абстрактний клас менш доречний:
Абстрактний клас зв'язував би всі сповіщувачі в єдину ієрархію успадкування, що є штучним обмеженням для класів з різною природою. Оскільки спільного стану (полів/властивостей) та базового коду немає, абстрактний клас створював би зайве жорстке зв'язування.

#### Фрагмент коду:
```csharp
public interface INotifier
{
    void Send(string message);
}

public class EmailNotifier : INotifier
{
    public string EmailAddress { get; set; }
    public EmailNotifier(string email) => EmailAddress = email;

    public void Send(string message) => Console.WriteLine($"[Email -> {EmailAddress}]: {message}");
}
```


### Сценарій 2: Обробка файлів

#### Обраний підхід: Абстрактний клас `FileProcessor`

#### Обґрунтування вибору:
У цьому сценарії використано **абстрактний клас**, оскільки:
1. **Наявність спільної логіки (Template Method):** Усі обробники файлів виконують однакову послідовність дій — відкриття файлу, обробка та закриття. Базові кроки (відкриття/закриття) мають спільну реалізацію, яка дублювалася б при використанні інтерфейсу.
2. **Спільний стан і базові властивості:** Усі обробники мають спільні характеристики, такі як `FileType` або базову конфігурацію, яку зручно зберегти в абстрактному класі.
3. **Перевикористання коду:** Абстрактний клас реалізує шаблонний метод `Process()`, де викликаються спільні методи `OpenFile()` / `CloseFile()` та абстрактний метод `ProcessContent()`, який перевизначають похідні класи.

#### Чому інтерфейс менш доречний:
Інтерфейси не дозволяють визначати стан (поля) та готову логіку (без порушення чистоти дизайну). Використання інтерфейсу змусило б дублювати код відкриття та закриття файлів у кожному конкретному класі.

#### Фрагмент коду:
```csharp
public abstract class FileProcessor
{
    public string FileType { get; protected set; }
    protected FileProcessor(string fileType) => FileType = fileType;

    public virtual void OpenFile(string filePath) => Console.WriteLine($"Відкриття {FileType}: '{filePath}'...");
    public abstract void ProcessContent(string filePath);
    public virtual void CloseFile(string filePath) => Console.WriteLine($"Закриття {FileType}: '{filePath}'.");

    public void Process(string filePath)
    {
        OpenFile(filePath);
        ProcessContent(filePath);
        CloseFile(filePath);
    }
}
```


## Загальні висновки щодо вибору між інтерфейсом та абстрактним класом

1. **Обирайте абстрактний клас, якщо:**
   - Потрібно надати спільну реалізацію методів для всіх похідних класів (перевикористання коду).
   - Класи мають тісний зв'язок "є" (IS-A) та спільний стан (поля, властивості).
   - Використовуються поведінкові шаблони проєктування, такі як *Шаблонний метод (Template Method)*.

2. **Обирайте інтерфейс, якщо:**
   - Необхідно визначити контракт поведінки для незалежних/непов'язаних класів.
   - Потрібна підтримка множинного успадкування поведінки.
   - Прагнете досягти максимального слабкого зв'язування та гнучкості для юніт-тестування.


## Контрольні запитання та відповіді

### 1. Які ознаки підказують, що сценарій краще моделювати через інтерфейс?
- Відсутність спільного стану (полів/властивостей) між класами.
- Потреба визначити лише спільну поведінку (контракт) для різнорідних класів, які не мають спільного предка.
- Потреба в множинній поведінці (клас реалізує декілька інтерфейсів).
- Прагнення до зменшення зв'язаності коду (Dependency Inversion Principle).

### 2. У чому перевага абстрактного класу для процесів зі спільними кроками виконання?
- Можливість реалізувати паттерн **Template Method (Шаблонний метод)**, де алгоритм із послідовними кроками описується в базовому класі, а специфічні кроки перевизначаються в похідних.
- Уникнення дублювання коду (DRY) для спільних кроків (наприклад, відкриття/закриття ресурсів, логування, валідація).
- Можливість зберігати спільний стан та мати доступ до `protected` членів.

### 3. Як порівняння двох підходів допомагає прийняти архітектурне рішення?
- Зіставлення вимог сценарію з особливостями ООП-конструкцій (інтерфейс vs абстрактний клас) дозволяє уникнути двох основних помилок:
  - Надмірного успадкування (створення жорсткої, негнучкої ієрархії, коли достатньо інтерфейсу).
  - Дублювання коду (копіювання одинакової логіки в різні класи, коли краще підійшов би абстрактний клас).
- Порівняння допомагає обрати підхід, який оптимізує підтримку, розширюваність та повторне використання коду.

### 4. Яку роль у ваших прикладах відіграє поліморфізм?
- **У сценарії 1 (Сповіщення):** Поліморфізм дозволяє зберігати різні типи сповіщувачів (`EmailNotifier`, `SmsNotifier`, `PushNotifier`) у єдиній колекції `List<INotifier>` і викликати метод `Send()` в циклі, не знаючи конкретного типу об'єкта.
- **У сценарії 2 (Обробка файлів):** Поліморфізм дозволяє обробляти різні формати файлів через єдину колекцію `List<FileProcessor>` і викликати шаблонний метод `Process()`, який динамічно спрямовує виконання до відповідної обробки `ProcessContent()`.
